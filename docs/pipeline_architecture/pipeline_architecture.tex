\begin{abstract}
\noindent
This report specifies, stage by stage, how the adaptive temporal search pipeline
turns a natural-language, multi-event query into a ranked list of candidate
videos and per-event timestamps. Every claim below is grounded directly in the
implementation (file and function cited in the margin notes) rather than in
the pipeline's design intent, and the report is organized around a single
worked example --- a four-event Vietnamese lion-dance query --- carried
end-to-end through a live run of the system. Section~\ref{sec:corrections}
collects the points where an informal description of the pipeline (as
commonly summarized by users of the system) diverges from what the code
actually does; the most consequential divergence is that video ranking is
\emph{not} built from a single per-video ``best candidate tuple'' with
cross-event structure, but from independently-scored per-event maxima that
are combined only at the very last step.
\end{abstract}

\section{Pipeline Overview}
% =====================================================================

The system answers a query of the form ``in this video corpus, find a video
that contains events $E_1, E_2, \dots, E_N$ in this description,'' returning,
for each candidate video, a best-guess timestamp for every event it appears to
contain. The pipeline has six stages, the first five automatic and the sixth
an explicit human-in-the-loop correction step.

\section{Stage 1: LLM Query Rewriting}
\label{sec:stage1}
% =====================================================================

\subsection{What it does}
A single batched call to a locally-hosted LLM (Ollama; model configured via
\code{OLLAMA\_MODEL}, default temperature 0) receives \emph{all} $N$ events
of the query at once, plus the shared \code{common\_query} string, and
returns one JSON object validated against a strict Pydantic schema
(\file{src/rewrite/schemas.py::RewriteResponse}). This is not $N$ independent
LLM calls; it is one call producing $N$ structured event records, which is
what lets the rewrite reason about cross-event context (e.g.\ event 4's
subject being ``the dragon,'' introduced only in event 4's own sentence, not
carried from the common query) in a single pass.

For every event the rewrite step must produce:
\begin{itemize}[nosep]
  \item \code{subject}, \code{action}, \code{visible\_state} --- the observable
    content of the target frame;
  \item \code{anchor\_query} --- a single, self-contained Vietnamese retrieval
    sentence for the target moment;
  \item \code{pre\_state}, \code{post\_state} --- the observable scene state
    immediately before and immediately after the target instant. These are
    what replace the temporal phrase itself (``khoảnh khắc đầu tiên,'' ``the
    first moment'') with something a frame-level image encoder can actually
    be compared against: an encoder cannot embed ``first,'' but it can embed
    ``two feet still off the ground'' versus ``all four feet on the ground'';
  \item \code{boundary} $\in \{$\code{start}, \code{end}, \code{state},
    \code{transition}, \code{interval}, \code{unknown}$\}$, mapped in
    \file{rewrite\_bridge.py::BOUNDARY\_MAPPING} onto the pipeline's internal
    \code{BoundaryType} (\code{start}$\to$\code{onset},
    \code{end}$\to$\code{offset}, \code{interval}$\to$\code{state});
  \item \code{temporal\_relation} --- \code{sequence\_start} / \code{after} /
    \code{before} / \code{during} / \code{simultaneous} / \code{independent},
    with a \code{reference\_event\_id} pointing at another event when
    applicable;
  \item exactly \textbf{two} Vietnamese and exactly \textbf{two} English
    retrieval-query variants (\code{retrieval\_queries\_vi},
    \code{retrieval\_queries\_en}, each \code{Field(min\_length=2,
    max\_length=2)} --- not ``up to two,'' \emph{exactly} two);
  \item \code{required\_entities}, \code{soft\_context},
    \code{excluded\_context}, \code{inferred\_information}, \code{ambiguities}
    --- provenance and hedging fields used for validation, not consumed by
    downstream ranking.
\end{itemize}

\corr{Note on \code{temporal\_relation}:} the schema captures explicit
ordering between events (which event follows which), but this report will
show in Section~\ref{sec:stage4} that \emph{nothing downstream reads this
field}. It is recorded but currently inert.

\subsection{Context propagation (``combine shared semantic of queries with
each query'')}
The mechanism for this is concrete, not just an LLM instruction. The server
extracts up to 12 lower-cased content words from \code{common\_query}
(\file{rewrite/service.py::\_extract\_context\_terms}, stopword-filtered via a
50-word Vietnamese function-word list) and requires each event's
\code{target\_moment\_vi}, \code{anchor\_query}, and every
\code{retrieval\_queries\_vi} entry to contain at least
$\min(2, |\text{terms}|)$ of them. If the LLM's first response fails this
check, \code{\_repair\_standalone\_context} deterministically prepends the
cleaned common-query text to the offending fields rather than re-prompting
indefinitely --- validation failures get at most one retry
(\code{MAX\_ANALYSIS\_ATTEMPTS = 2}) before falling back to this mechanical
repair.

\section{Stage 2: Per-Variant Sparse Retrieval and RRF Fusion}
% =====================================================================
\label{sec:stage2}

\subsection{Retrieval}
Each event carries up to \code{query\_variants\_per\_event = 4} retrieval
strings (2 Vietnamese + 2 English from Stage 1). Each variant is sent
\emph{independently} to an external sparse-retrieval microservice
(\file{src/adaptive\_search/client.py::UpstreamSearchClient.search}, base URL
configured via \code{UPSTREAM\_URL}), requesting up to
\code{top\_n\_per\_variant = 500} ranked frame candidates. Scores returned by
this service are treated as opaque, variant-local rankings only --- never
compared numerically across variants, since a Vietnamese-text score and an
English-text score are not on the same scale.

\subsection{Reciprocal Rank Fusion}
\file{retrieval.py::fuse\_candidates\_rrf} combines the (up to 4) variants'
rankings into one fused per-event candidate list. For each event, and for
each of its query variants independently:
\begin{enumerate}[nosep]
  \item deduplicate to one row per physical frame $(\text{video\_id},
    \text{frame\_id})$, keeping the highest-scoring row;
  \item rank the deduplicated frames by \code{raw\_relevance\_score}
    descending, keep the top \code{top\_n\_per\_variant};
\end{enumerate}
then, across all variants that placed a given frame in their own top list,
accumulate
\begin{equation}
  \mathrm{RRF}(f) \;=\; \sum_{v \,:\, f \in \text{top}_v} \frac{1}{k + \mathrm{rank}_v(f)},
  \qquad k = \code{rrf\_k} = 60,
  \label{eq:rrf}
\end{equation}
where $\mathrm{rank}_v(f)$ is $f$'s 1-indexed rank inside variant $v$'s own
top list. The fused list is then re-sorted by $\mathrm{RRF}(f)$ descending and
truncated to \code{top\_n\_fused = 1000} \emph{per event}. Fusion is scoped
strictly per \code{(session\_id, event\_id)}
(\code{retrieval.py} line 27) --- variants belonging to different events are
never mixed, ``so four rewrite variants do not accidentally become four
temporal events'' (source comment, \file{retrieval.py} lines 20--21).

Each surviving fused candidate becomes a new \code{SparseCandidate} whose
\code{raw\_relevance\_score} \emph{is} the RRF score from
Eq.~\ref{eq:rrf} (not the original upstream score), whose
\code{timestamp\_seconds} is inherited from whichever contributing variant
had the single highest raw upstream score for that frame, and whose
\code{query\_variant} field is stamped \code{"rrf:vi\_1,vi\_2,en\_1"} etc.\
recording provenance.

\section{Stage 3: Temporal Region Clustering}
% =====================================================================
\label{sec:stage3}

\corr{Production update (Section~\ref{sec:tuple-round7}):} this section
describes \code{cluster\_temporal\_regions} and
\code{merge\_overlapping\_regions}, which are no longer called from the
production retrieve path as of Round 7 of the tuple-ranking methodology
(Section~\ref{sec:tuple-ranking}) --- clustering and merging were found to
have zero effect on either downstream consumer that used to justify them
(Stage 4's ranking, Stage 5's refinement seeding), and were replaced by
\code{algorithms.py::atomic\_regions}: one region per candidate, never
merged, padded by a fixed \code{margin\_seconds} on each side (reusing this
section's own \code{margin\_seconds} default, 3.0s) purely so a region still
has real width for \code{replace\_frame\_scores}' span check. What follows
describes the clustering \emph{algorithm}, still real, tested code
(\file{algorithms.py}), still the comparison arm the production decision
rests on --- just not what a live session runs today. Applied to this
section's own worked example below, the current behavior would be: 353
candidates $\to$ 353 regions (one each, not 309), every region padded to
\code{[t-3, t+3]}, no merging step at all.

\subsection{Clustering}
\file{algorithms.py::cluster\_temporal\_regions} groups the fused candidates
from Stage 2, separately per $(\text{event\_id}, \text{video\_id})$ pair.
Within each group, candidates are sorted by timestamp and split greedily: a
new cluster starts whenever
\[
  t_i - t_{i-1} > \code{gap\_seconds} = 3.0\text{s}
  \quad\text{or}\quad
  t_i - t_{\text{cluster start}} > \code{max\_core\_span} = 24.0\text{s},
\]
where $\code{max\_core\_span} = \code{max\_region\_seconds} - 2 \times
\code{margin\_seconds} = 30.0 - 2(3.0)$. Each resulting cluster becomes one
provisional \code{TemporalRegion} spanning
$[\,t_{\min}-\code{margin\_seconds},\; t_{\max}+\code{margin\_seconds}\,]$
(clamped at 0), i.e.\ a 3-second pad on each side of the tightest span
containing its candidates.

\subsection{Region scoring}
Each region gets two scores:
\begin{align}
  \code{raw\_coarse\_score}(\rho) &= \max_{c \in \rho} \; \mathrm{RRF}(c),
  \label{eq:region-raw}\\
  \code{normalized\_coarse\_score}(\rho) &= \max_{c \in \rho} \;
    \mathrm{RobustSigmoid}_{\,\text{event}(\rho)}(\mathrm{RRF}(c)),
  \label{eq:region-norm}
\end{align}
i.e.\ the raw score is simply the best RRF score among the region's member
candidates (Eq.~\ref{eq:region-raw}); the normalized score
(Eq.~\ref{eq:region-norm}) applies a robust, outlier-resistant
median/MAD sigmoid calibration
(\code{algorithms.py::robust\_sigmoid}: $z = \mathrm{clip}\!\left(
\frac{x - \mathrm{median}}{1.4826\,\mathrm{MAD}}, \pm 8\right)$, then
$\sigma(z)$) computed once over \emph{all} of that event's fused candidates
(population-relative, not per-region), and takes the max over the region's
members of that population-relative score. This is the score that Stage 4
actually consumes.

\subsection{Merging}
\file{algorithms.py::merge\_overlapping\_regions} then unions any two regions
in the same $(\text{session}, \text{event}, \text{video}, \text{status})$
group whose (already margin-expanded) spans overlap, provided the merge would
not push the combined span past \code{max\_region\_seconds = 30}s; the merged
region's scores are the max of its two parents' scores, and its
\code{candidate\_ids} the union.

\section{Stage 4: Video Prioritization}
% =====================================================================
\label{sec:stage4}

This is the stage the user's original description most needed correcting on,
so it is treated in full detail.

\subsection{Per-event, per-video best score}
\file{algorithms.py::prioritize\_videos} builds, for every video $v$ that has
\emph{any} surviving region, a per-event best score:
\begin{equation}
  s(v, e) \;=\; \max_{\rho \,:\, \mathrm{video}(\rho)=v,\; \mathrm{event}(\rho)=e}
    \code{normalized\_coarse\_score}(\rho),
  \label{eq:best-event-score}
\end{equation}
i.e.\ ``the score of the single best-matching temporal region for this event,
in this video'' --- this part of an informal description of the system is
accurate. \corr{What is \emph{not} accurate is calling this a ``candidate
tuple.''} No object bundling one timestamp per event, ordered or otherwise,
is constructed at this stage (or anywhere in the code path this endpoint
calls) --- see \ref{sec:no-tuple} below.

\subsection{Combining across events}
For a query with events $e_1,\dots,e_N$, define the video's \emph{score
vector} $\mathbf{s}(v) = \big(s(v,e_1),\dots,s(v,e_N)\big)$, substituting
$s(v,e_i) = 0$ when $v$ has \emph{no} surviving region for $e_i$ at all (an
uncovered event, not a missing/excluded one). Then:
\begin{align}
  \mathrm{cov}(v) &= \bigl|\{\, i : v \text{ has} \ge 1 \text{ region for } e_i \,\}\bigr|
    \quad(\code{event\_coverage}),\\
  \mathrm{ncov}(v) &= \mathrm{cov}(v) / N \quad(\code{normalized\_coverage}),\\
  \mu(v) &= \tfrac{1}{N}\textstyle\sum_i s(v,e_i) \quad(\code{mean\_best\_event\_score};
    \text{ arithmetic mean over \emph{all} $N$ slots}),\\
  m(v) &= \min_i s(v,e_i) \quad(\code{min\_best\_event\_score}),\\
  \mathrm{priority}(v) &= \frac{w_c\, \mathrm{ncov}(v) + w_\mu\, \mu(v) + w_m\, m(v)}
    {w_c + w_\mu + w_m} \quad(\code{priority\_score}).
  \label{eq:priority}
\end{align}
Videos are ranked by $\bigl(-\mathrm{priority}(v), -\mathrm{cov}(v),
\code{video\_id}\bigr)$ lexicographically.

\textbf{Current production weights} (\file{schemas.py} lines 157--159,
comment: ``winner config from the \dots{} hyperparameter sweep: mean-only
ranking beat every blend that included coverage or min once retrieval is
wide''):
\begin{gather*}
  w_c = \code{video\_coverage\_weight} = 0.0, \qquad
  w_\mu = \code{video\_mean\_weight} = 1.0, \\
  w_m = \code{video\_min\_weight} = 0.0,
\end{gather*}
so in production $\mathrm{priority}(v) = \mu(v)$ exactly.

\corr{Correction to a common simplification:} it is tempting to read
$w_c = w_m = 0$ as ``coverage doesn't affect ranking, only the displayed
`Matched $k/N$' label does.'' That is \emph{false}. Because uncovered events
are zero-filled into the mean (Eq.~\ref{eq:priority}'s $\mathbf{s}(v)$
definition), a video missing one of $N$ events has its
\code{mean\_best\_event\_score} silently divided by the same $N$ as a video
that found all of them --- i.e.\ \textbf{coverage is not a separate ranking
term, but it is not ``zero-weight'' either: it acts through the mean's
denominator}, not through $w_c$.

\subsection{\corr{There is no cross-event ``candidate tuple'' at this stage}}
\label{sec:no-tuple}
The codebase \emph{does} contain machinery for exactly the kind of object an
informal description implies --- an ordered, per-video tuple of one timestamp
per event, scored jointly with adjacent-gap penalties:
\code{algorithms.py::assemble\_ordered\_tuples}, together with
\code{adjacent\_hinge\_penalty} and the \code{TupleResult} schema
(\file{schemas.py} lines 474+, which validates that a tuple's per-event
timestamps are strictly ordered and computes
\code{raw\_gap\_penalty}/\code{raw\_constraint\_bonus} between adjacent
events). \textbf{But this machinery is wired to a different command
path.} It runs inside \code{AdaptiveSearchService.replace\_frame\_scores}
(\file{service.py} line 358, \code{\_rebuild\_tuples}), which requires the
\emph{caller} to have already computed and submitted dense per-frame
embedding scores via \code{POST
.../search-sessions/\{id\}/artifacts/frame-scores}. The live Search page's
``Refine timestamps'' checkbox never calls that endpoint --- it calls
\code{GET .../video-priorities?apply\_boundary\_refinement=true}, which is
served by \code{router.py::\_video\_priority\_with\_boundary\_refinement}
(Section~\ref{sec:stage5}), a function that reads only
\code{bundle.artifacts.regions} and \code{bundle.session.constraints};
it does not touch \code{bundle.artifacts.tuples},
\code{.frontier\_region\_ids}, or \code{.proposals} at all.

\textbf{Practical consequence.} Because ranking and refinement each pick a
timestamp per event completely independently of every other event, nothing
in the live pipeline enforces $t(e_1) < t(e_2) < \dots$, and nothing prevents
two different events from independently converging on the same physical
frame. Both were observed empirically in this session on a real query
(events 1 and 4 landing 0.13s apart at the same point in a video, with event
1's timestamp \emph{after} events 2 and 3's) --- this is not a bug, it is the
direct, predictable consequence of the architecture described in this
section, and it is the reason the interactive per-event manual-fix feature in
Stage 6 exists.

\section{Stage 5 (opt-in): Per-Event Boundary Refinement}
% =====================================================================
\label{sec:stage5}

Requested via \code{apply\_boundary\_refinement=true}; without it, Stage 4's
output is the final answer, and \emph{no} per-event timestamp is exposed at
all (the \code{VideoPriority} schema, \file{schemas.py} lines 465--471, has
no timestamp field --- only \code{event\_coverage},
\code{normalized\_coverage}, \code{mean\_best\_event\_score},
\code{min\_best\_event\_score}, \code{priority\_score}). Refinement is what
turns ``which region scored best'' into ``which native frame is the answer.''
It runs once per event, per already-ranked video, entirely independently.

\subsection{Seed selection}
\file{boundary\_seeds.py::select\_event\_seeds}, for one $(e, v)$ pair: rank
that pair's regions by \code{raw\_coarse\_score} (Eq.~\ref{eq:region-raw},
\emph{not} the normalized score), keep whichever are within
\code{SCORE\_THRESHOLD\_RATIO = 10\%} of the best, capped at
\code{MAX\_REGIONS\_PER\_EVENT = 2}; pool those regions' member candidates,
sort by each candidate's own \code{raw\_relevance\_score}, cap at
\code{MAX\_SEEDS\_PER\_EVENT = 6}. \corr{Only the single best seed
(\code{seeds[0]}) is ever passed to refinement} --- the module's own
docstring is explicit that comparing scores across several independently
swept seed neighborhoods ``was tried and found structurally invalid''; the
other up to 5 seeds exist only to make the top pick more likely correct, not
to be independently refined and compared.

\subsection{Native-fps neighborhood search}
Around that one seed timestamp $t_0$ (converted to a native frame index via
$\lfloor t_0 \cdot \mathrm{fps} \rceil$), \code{boundary\_refinement.py::refine\_event\_boundary}
decodes the real video at native resolution for offsets
$-\code{radius\_frames}, \dots, +\code{radius\_frames}$
(\textbf{default 10}, i.e.\ up to 21 frames, clamped to the video's actual
duration) via the configured \code{FrameProvider}.

\subsection{Text--image scoring}
Each sampled frame's image embedding is compared, via cosine similarity, to
three separate text embeddings --- \code{anchor\_query}, \code{pre\_state},
\code{post\_state} (falling back to \code{anchor\_query} when a state string
is absent) --- using a shared dual encoder, \textbf{SigLIP2}
(\code{google/siglip2-base-patch16-224} by default;
\file{embedding.py::score\_event\_frames}). An optional, disabled-by-default
``quality profile'' can instead route through \code{Qwen3-VL-Embedding-2B}
(and an optional \code{Qwen3-VL-Reranker-2B} reranking pass), gated by
\code{quality\_profile\_enabled} / \code{use\_reranker} (both \code{False} in
production).

\subsection{Boundary-profile-aware proposal scoring}
\file{proposal\_profiles.py::generate\_profiled\_proposals} dispatches on the
event's \code{boundary\_type}:
\begin{itemize}[nosep]
  \item \textbf{transition} (\code{onset}, \code{offset}, \code{transition},
    \code{plateau\_start} --- i.e.\ \code{boundary="start"} or
    \code{"end"} from Stage 1, which is what all four events of the worked
    example use): \code{algorithms.py::generate\_boundary\_proposals}
    tries every combination of left/right window sizes from
    \code{window\_options\_seconds} = (0.5, 1.0, 2.0, 3.0)s (requiring
    $\ge$ \code{min\_samples\_per\_side} = 2 samples on each side) and scores
    \begin{align}
      \mathrm{raw\_boundary} &= 0.5 \cdot (\mathrm{post\_persistence} -
        \overline{\mathrm{post}}_{\mathrm{left}})
        + 0.5 \cdot (\mathrm{pre\_consistency} - \overline{\mathrm{pre}}_{\mathrm{right}})
        + 0.1 \cdot \mathrm{motion} \notag\\
        &\quad - 0.01\cdot\frac{w_L+w_R}{2 w_{\max}}
        - 0.01\cdot\frac{|w_L-w_R|}{w_{\max}},
    \end{align}
    i.e.\ how much more the right side resembles \code{post\_state} than the
    left side does (contrast, not raw similarity), plus the symmetric
    pre-state contrast, plus a motion term (currently hard-coded to 0
    everywhere in this codebase --- no motion signal is implemented), with a
    small penalty for wider or more asymmetric windows. The
    highest-\code{raw\_boundary} window per candidate center is kept, then
    calibrated across the whole neighborhood via robust-sigmoid
    ($\code{anchor\_clip\_z} = 8$) into $\mathrm{normalized\_boundary}$.
  \item \textbf{state}: uses local temporal persistence of the anchor score
    instead of a left/right contrast (appropriate for a state predicate with
    no directional edge).
  \item \textbf{symmetric\_peak}: scores center prominence relative to both
    flanks.
\end{itemize}
In every profile, the final per-frame score is the same weighted blend:
\begin{equation}
  \mathrm{final\_event\_score} = \frac{
    0.4 \cdot \mathrm{semantic} + 0.3\cdot\mathrm{boundary}
    + 0.1\cdot\mathrm{pre\_consistency} + 0.2\cdot\mathrm{post\_persistence}
  }{0.4+0.3+0.1+0.2},
  \label{eq:final-event-score}
\end{equation}
where $\mathrm{semantic}$ is the (population-calibrated) anchor-query cosine
similarity at that exact frame. The single frame maximizing
Eq.~\ref{eq:final-event-score} within the searched neighborhood is the
event's refined timestamp for that video.

\subsection{Independence and its consequence}
This entire computation --- seed, neighborhood, scoring, arg-max --- runs
once per event with no reference to any other event's chosen frame,
timestamp, or even existence. This directly explains an anomaly observed
this session on a real result (video \texttt{BK80fNF9ysI}, 4/4 events
matched): event 1 was refined to $4{:}01.14$ and event 4 to $4{:}01.01$
(0.13s apart, i.e.\ the same physical frame within refinement's own
$\pm 10$-native-frame search radius), while event 1's timestamp fell
\emph{after} events 2 ($3{:}05.75$) and 3 ($3{:}42.25$) despite being listed
first in the query. Neither is a defect in the sense of a malfunction; both
are the predictable result of Section~\ref{sec:no-tuple}: each event is its
own independent arg-max over Eq.~\ref{eq:final-event-score}, with no
ordering or mutual-exclusivity constraint tying it to its siblings.

\subsection{User-fix short-circuit}
Before any of the above runs for a given $(e,v)$,
\code{\_video\_priority\_with\_boundary\_refinement} checks
\code{bundle.session.constraints.event\_constraints[e]}. If the user has
already fixed a frame for $e$ in $v$ via \code{commands/fix-frame}
(Section~\ref{sec:stage6}), that timestamp is emitted directly, tagged
\code{"source": "user\_fixed"}, and \emph{neither} seed selection nor the GPU
scoring pass runs at all for that event --- confirmed by a dedicated test
(\file{tests/adaptive\_search/test\_adaptive\_video\_priorities\_refinement.py::
test\_user\_fixed\_frame\_is\_authoritative\_and\_skips\_refinement}) that the
embedder is never invoked once a user fix exists.

\section{Stage 6: Interactive Correction}
% =====================================================================
\label{sec:stage6}

The client (Streamlit UI) closes the loop opened in
Section~\ref{sec:no-tuple}/\ref{sec:stage5}: since no automatic mechanism
enforces cross-event consistency, a human reviewing the returned frames is
the actual correction mechanism for ordering/collision errors, and for
events the pipeline never found any region for at all.

\begin{itemize}
\item \textbf{Reject-and-replace (video level).} Rejecting a video adds it to
  \code{constraints.rejected\_video\_ids} (\code{PUT .../constraints}) and the
  server genuinely re-ranks (\code{prioritize\_videos} re-run with the video
  excluded via \code{\_region\_allowed}), promoting the next-best video ---
  not a client-side filter of an already-fetched page.
\item \textbf{Free-form manual frame correction (event level).} A new
  endpoint, \code{GET /media/\{video\_id\}/frame-preview}, decodes real
  native-fps frames around an arbitrary \code{anchor\_seconds} (default
  radius \textbf{15} frames --- note this is a different default from Stage
  5's automatic radius of 10; both are independently configurable) and
  returns them as base64 JPEGs. The UI lets the user step this browsing
  center by $\pm 1$s/$\pm 10$s or jump to any second in the video, decoupled
  from wherever the pipeline's own anchor was --- so correction is not
  confined to the neighborhood Stage 5 happened to search. Picking a frame
  calls \code{commands/fix-frame} with an arbitrary
  \code{(video\_id, frame\_id, timestamp\_seconds)}; the endpoint accepts
  this for \emph{any} event belonging to the session, whether or not that
  event previously had any candidate in that video at all --- which is what
  makes it possible to manually supply a timestamp for an event Stage 2--4
  never found any region for (the ``matched 3/4, need to fix the 4th''
  case). The written constraint is what Section~\ref{sec:stage5}'s
  short-circuit later reads as authoritative.
\item \textbf{Scope boundary.} This entire stage requires a session
  (\code{event\_id} must belong to \code{bundle.session.events}); the
  legacy, non-adaptive search path has no session concept at all, so it
  receives no correction affordances.
\end{itemize}

\section{Methodology: Multi-Region Pooling and Order-Aware Tuple Ranking}
\label{sec:tuple-ranking}
% =====================================================================

Section~\ref{sec:no-tuple} established that Stage 4 has no mechanism for
cross-event reasoning: each event's contribution to a video's score is an
independent maximum (Eq.~\ref{eq:best-event-score}), and Stage 5 seeds each
event's refinement independently of every other event
(Section~\ref{sec:stage5}, ``Independence and its consequence''). This
section documents a proposed extension addressing that gap directly ---
its design, the three rounds of ablation it was validated under, and its
integration into the live service as an opt-in mode --- rather than a
correction to the existing pipeline description.

\subsection{Motivation}
Two properties of Stages 2--5 compound into the failure mode
Section~\ref{sec:stage5} demonstrated on \texttt{BK80fNF9ysI}. First,
retrieval deliberately casts a wide net per event
(\code{top\_n\_fused}=1000, Section~\ref{sec:stage2}) and clustering can
leave several distinct regions per event per video
(Section~\ref{sec:stage3}), yet Eq.~\ref{eq:best-event-score} collapses
that entire pool to a single number via $\max$, and
\file{boundary\_seeds.py::select\_event\_seeds} (Section~\ref{sec:stage5})
collapses it again to a single seed --- \code{seeds[0]} --- before
refinement ever runs. Second, because that arg-max is taken independently
per event, nothing in the pipeline can express or reward the fact that a
query's events are expected to occur in a particular temporal order. Both
properties are architectural, not incidental: the pipeline was deliberately
built this way to keep Stage 4 cheap (CPU-only, no embedder) and Stage 5's
search local (Section~\ref{sec:stage5}, ``the module's own docstring is
explicit that comparing scores across several independently swept seed
neighborhoods `was tried and found structurally invalid'''). The design
question this section answers is whether cross-event structure can be
reintroduced \emph{without} reintroducing the cost that motivated removing
it in the first place --- i.e.\ entirely within the cheap, region-score
stage, never touching the embedder.

\subsection{Design}
\label{sec:tuple-design}

\subsubsection{Multi-region pooling}
For an $(e, v)$ pair, instead of retaining only the arg-max region, pool
every region within an absolute floor $\alpha$ and a relative band $\delta$
of the best. Writing $s(\rho)$ for \code{normalized\_coarse\_score}$(\rho)$
(Eq.~\ref{eq:region-norm}) and $\rho^\star = \max_\rho s(\rho)$:
\begin{equation}
  \mathrm{pool}(e, v) = \bigl\{\, \rho : \mathrm{event}(\rho){=}e,\ \mathrm{video}(\rho){=}v,\
    s(\rho) \ge \alpha,\ s(\rho) \ge \rho^\star - \delta \,\bigr\}[{:}N],
  \label{eq:pool}
\end{equation}
where $[{:}N]$ denotes best-score-first truncation at
\code{max\_regions\_per\_event}. Because $\rho^\star$ itself always
satisfies both conditions, $\mathrm{pool}(e,v)$ is never empty when at
least one region exists, and always contains the single region
Eq.~\ref{eq:best-event-score} would have picked --- this is what makes the
correctness invariant of Section~\ref{sec:tuple-invariant} provable rather
than merely observed.

\subsubsection{Tuple assembly and order scoring}
For a video with pools $\mathrm{pool}(e_1,v),\dots,\mathrm{pool}(e_N,v)$
(a region missing entirely, i.e.\ $\mathrm{pool}(e_i,v)=\varnothing$, is
represented as a single placeholder choice contributing $0$ to the mean
below and no timestamp --- the same zero-fill convention as
Eq.~\ref{eq:priority}, not a reason to drop the video), every combination
choosing one member per event is a candidate tuple, enumerated by bounded
backtracking capped at \code{max\_combinations\_per\_video} (best-region-first
per event, so truncation drops the least-promising combinations first, not
an arbitrary prefix). For a chosen tuple $c=(\rho_1,\dots,\rho_N)$ with
representative timestamps $t_i$ (each region's own best-scoring member
candidate's timestamp --- the same quantity \code{select\_event\_seeds}
would return as \code{seeds[0]} for that region alone):
\begin{equation}
  \mathrm{order}(c) = \frac{2 \cdot |\{(p,s) \in C : t_s > t_p\}| - |C|}{|C|}
  \ \in [-1, 1],
  \label{eq:order-score}
\end{equation}
where $C$ is a set of \emph{directional} constraints, each pair
$(p,s)$ meaning ``event $p$'s timestamp is expected to precede event $s$'s,''
restricted to pairs where both $t_p,t_s$ are defined (an uncovered event
drops any constraint touching it, imposing no ordering requirement on its
neighbors). \corr{A correctness fix applied during this work:} $C$ must be
built from each event's actual claimed relation to another event
(\code{reference\_event\_id}, Section~\ref{sec:stage1}), \emph{not} from
adjacent query-list position. An earlier implementation used the adjacent
chain $C=\{(1,2),(2,3),\dots\}$ unconditionally; if a query ever describes
event $i$ as \code{after} a \emph{later-listed} event $j$ (relation
direction disagreeing with list position, which the rewrite stage's own
grounding rules in Section~\ref{sec:stage1} permit and do not forbid), that
implementation would score the pair backwards --- rewarding exactly the
violation the relation claims. The fix replaces the boolean
``check this adjacent pair or not'' with explicit
$(p,s)$ pairs derived from relation direction; $C$ defaults to the adjacent
chain only when no relation data is available for a video.
Verified by a unit test reproducing this exact scenario: relation
``event~0 after event~1'' with timestamps ordered so that event~0 precedes
event~1 must score Eq.~\ref{eq:order-score} as $-1$ (a violation), not the
$+1$ a list-position check would have produced.

\corr{A second fix, Section~\ref{sec:tuple-round4}:} direct edges alone
under-use the relation graph. \code{build\_order\_constraints}
(\file{tuple\_ranking.py}) now closes $C$ \emph{transitively} --- given
direct edges $A\!\to\!B$ and $B\!\to\!C$ (from two separate events' own
\code{reference\_event\_id}s), it also derives $A\!\to\!C$ via reachability
over the (small, per-query) event graph, so order-checking is not limited to
pairs some event directly references. \code{during} and \code{simultaneous}
relations still contribute no edge, but this is now an explicit, documented
branch (this pairwise-precedence model has no correct encoding for
temporal overlap/proximity; asserting a direction would be wrong as often as
right) rather than a silent fallthrough. \code{EventDefinition}
(\file{schemas.py}) was also extended with real \code{temporal\_relation}/
\code{reference\_event\_id} fields, populated by \file{rewrite\_bridge.py}
from the actual rewrite output (Section~\ref{sec:stage1}) --- $C$ is built
from live session data in production today, not only from this section's
offline benchmark cache.

\subsubsection{Confidence-gated order weight}
An unconditional order bonus was found, in Round 1
(Section~\ref{sec:tuple-round1}), to help videos where the underlying
region scores already carry real signal and actively mislead where they do
not --- rewarding two candidates' being ``in order'' is only evidence of
anything when those candidates are themselves plausible. The order term's
weight is therefore scaled by the tuple's own mean region score before
being applied:
\begin{equation}
  w_{\mathrm{eff}}(c) =
  \begin{cases}
    w_o & \text{gate} = \code{none} \\
    w_o \cdot \mu(c) & \text{gate} = \code{linear} \\
    w_o \ \text{if}\ \mu(c) \ge \tau\ \text{else}\ 0 & \text{gate} = \code{threshold}
  \end{cases}
  \label{eq:gate}
\end{equation}
where $\mu(c) = \frac{1}{N}\sum_i \code{normalized\_coarse\_score}(\rho_i)$
(the tuple's mean region score, $0$ for an uncovered event's placeholder)
and $\tau=$ \code{confidence\_gate\_threshold}. A tuple's final score is
\begin{equation}
  \mathrm{score}(c) = \mu(c) + w_{\mathrm{eff}}(c) \cdot \mathrm{order}(c),
  \label{eq:tuple-score}
\end{equation}
and a video's score is either the best tuple's score
(\code{pooling=}\code{"max"}) or the mean of its kept tuples
(\code{pooling=}\code{"mean"}, capped at \code{max\_tuples\_per\_video}).

\subsubsection{Correctness invariant}
\label{sec:tuple-invariant}
At $w_o=0$, Eq.~\ref{eq:tuple-score} reduces to $\mu(c)$ alone, and because
$\mathrm{pool}(e,v)$ always contains each event's independently-best
region (Eq.~\ref{eq:pool}), the unconstrained best combination is provably
just ``each event's own best region'' --- exactly what
Eq.~\ref{eq:best-event-score}/\ref{eq:priority} already compute. Video
ranking under this design at $w_o=0$ must therefore reproduce
\file{algorithms.py::prioritize\_videos} byte-for-byte, modulo tie-breaks.
This was verified twice: as a unit test on synthetic regions, and --- more
importantly, since it is the one property that must hold before any
benchmark result can be trusted --- reproduced exactly on real data in every
round below.

\subsection{Experimental Methodology}
\label{sec:tuple-experiment}
All results in this section come from real, live infrastructure: the
production sparse-retrieval service (via
\file{adaptive\_search/dependencies.py::upstream\_search\_client}), real
YouCook2 recipe videos, and, for Round 2's \code{temporal\_relation}
condition, the real LLM rewrite service (Section~\ref{sec:stage1}) run once
per video and cached. No result below is synthetic or hand-computed.

\textbf{Sample.} $n=30$ videos (first 30, sorted, of 203 available query
files), matching this codebase's existing benchmark convention
(\file{irrelevant\_things/benchmarks/youcook2/}).

\textbf{Paired, noise-free comparison.} For each video, real upstream
candidates are fetched \emph{once}, fused and clustered \emph{once}
(clustering hyperparameters were separately confirmed invariant to this
question --- sweeping \code{gap\_seconds}/\code{margin\_seconds}/
\code{max\_region\_seconds} across nine configurations spanning a 600$\times$
range changed neither ranking nor refinement seeds on this same real data).
Every swept configuration of this section's algorithm is then evaluated
offline, in Python, against that one fetched/clustered dataset --- the
established ``fetch once, sweep cheaply'' pattern this codebase already
uses for its other hyperparameter sweeps
(\file{hyperparameter\_sweep\_results.md}).

\textbf{Metrics.} The repository's existing definitions
(\file{boundary\_metrics.py}), reused unmodified for direct comparability
with prior benchmark documents:
\begin{align}
  \code{recall@k\_new}(\mathrm{rank}, \mathrm{hits}) &= \mathrm{hits}\ \text{if}\ \mathrm{rank}\le k\ \text{else}\ 0,\\
  \code{final\_query\_score} &= \mathrm{mean}_{k \in \{1,5,20,50,100\}}\ \code{recall@k\_new},
\end{align}
where $\mathrm{rank}$ is the ground-truth video's position and
$\mathrm{hits}$ is how many of its own events' anchor timestamps fall
inside their annotated ground-truth interval --- a joint measure of ranking
quality (Branch A) \emph{and} anchor quality (Branch B), since this design
changes both simultaneously (Section~\ref{sec:tuple-integration}).

\subsubsection{Round 1: core proposal ablation}
\label{sec:tuple-round1}
Swept $\delta \in \{0.05, 0.10, 0.15, 0.25, 0.40\}$, $N \in \{1,\dots,20\}$,
$w_o \in \{0, 0.05, 0.1, 0.2, 0.4, 0.8\}$, and \code{pooling}
$\in\{\code{max},\code{mean}\}$, at $C$ defaulting to the adjacent chain
(no \code{temporal\_relation} data used yet).

\subsubsection{Round 2: relation-aware constraints, confidence gating, deeper pooling}
\label{sec:tuple-round2}
Three follow-up questions, each requiring new infrastructure: (i) does
building $C$ from real \code{temporal\_relation} data change anything ---
required one real LLM rewrite call per video (Section~\ref{sec:stage1}),
cached to \file{runs/temporal\_relations\_cache.jsonl} (29/30 succeeded; one
failed on an unrelated schema-validation error and fell back to the
adjacent-chain default); (ii) does Eq.~\ref{eq:gate} recover the tail-recall
regression Round 1's unconditional $w_o$ found --- tested
\code{gate}$\in\{\code{none},\code{linear},\code{threshold}\}$ at
$\tau\in\{0.3,0.5,0.7\}$; (iii) does pooling deeper than $N=20$ help ---
tested $N\in\{30,50,100,200\}$, with \code{max\_combinations\_per\_video}
raised to $5{\times}10^5$ so the wider pools were not silently truncated by
the same cap that (at default settings) already binds at $N{=}20$
($20^4=160{,}000 > 20{,}000$).

\subsubsection{Round 3: a correctness fix, re-validated}
\label{sec:tuple-round3}
The list-position bug described in Section~\ref{sec:tuple-design} was found
by direct code review, not by any benchmark discrepancy, and fixed as
described there. The full sweep was re-run after the fix; results were
byte-for-byte identical to Round 2, which is itself informative: every real
\code{after} relation observed in this corpus referenced the immediately
preceding list index (Section~\ref{sec:tuple-results}), so the buggy and
fixed implementations happened to agree on every video tested --- the bug
was real and reachable in principle, never triggered on this sample, and is
now closed for any future query where list order and claimed chronology
diverge.

\subsubsection{Round 4: two limitations closed, $n$ doubled to 60, a no-clustering ablation}
\label{sec:tuple-round4}
Three follow-ups: (i) fix the two remaining scope gaps that most needed it --- transitive relation
closure and \code{EventDefinition} actually carrying \code{temporal\_relation} in production
(both described in Section~\ref{sec:tuple-design}); (ii) double the sample to $n=60$ (the
\code{temporal\_relations\_cache} was extended the same way: 60/60 cached, one unrelated
schema-validation failure, still 100\% \code{after} across all 176 classified adjacent pairs ---
the corpus property Round 3 found at $n=30$, confirmed at double the sample); (iii) test whether
Stage 3 (\file{algorithms.py::cluster\_temporal\_regions}) matters for tuple ranking specifically,
by building an \emph{atomic} region set --- one \code{TemporalRegion} per candidate, no clustering
at all --- from the same fused candidates, and running the full sweep against both region sets in
parallel. Both fixes are covered by 34 unit tests (up from 26) and 6 HTTP integration tests (up
from 5), including a test that constructs a live session where an event is listed first but is
explicitly \code{after} a later-listed event, and confirms refinement picks the anchor the
\emph{relation} implies through the real HTTP $\to$ RRF $\to$ clustering pipeline, not the one list
position would have implied.

\subsubsection{Round 5: fine-grained $\tau$ sweep and the full atomic-region grid}
\label{sec:tuple-round5}
Two follow-ups to Round 4's own limitations: (i) sweep $\tau$ at $0.05$ resolution (19 points,
$0.05$--$0.95$) for both the existing mean-score gate and a new \emph{margin}-based gate, find the
best $\tau$ for each, and compare them; (ii) extend the no-clustering ablation past its Round 4
subset (\code{default}, $N\in\{1,5,20\}$, \code{pooling=mean}) to the full grid Rounds 1--2 swept
under clustering (\code{delta}$\in\{0.05,0.10,0.15,0.25,0.40\}$, $N\in\{1,2,3,5,10,20,30,50,100,200\}$,
\code{order\_weight}$\in\{0.05,0.2,0.4,0.8\}$, \code{pooling}$\in\{$\code{max},\code{mean}$\}$).

\code{\_region\_margin(region, pool)} (\file{tuple\_ranking.py}) computes, for the \emph{specific}
region a combination actually selects for an event (not a pool-level constant): if that region is
the pool's top scorer, the gap to the runner-up; otherwise the (negative) gap between the
reached-for region's own score and the pool's actual top score --- correctly signaling lower
confidence the further down the pool a tuple reached to satisfy the order term. Single-member pools
fall back to the region's own score. \code{confidence\_gate="margin"} routes this per-event value
(meaned across the tuple) through the exact same hard-cutoff shape as \code{"threshold"}
(\code{\_effective\_order\_weight}), so the two signals are compared apples-to-apples: identical gate
shape and $\tau$ grid, only the confidence value differs. Covered by 4 new unit tests (39 total, up
from 34).

\subsubsection{Round 6: the missing combo, and the production switch to atomic regions}
\label{sec:tuple-round6}
Round 5's atomic-region grid never combined atomic regions with \code{temporal\_relation} gating ---
the flagship ``production'' configuration was only ever benchmarked on clustered regions. This round
adds the one missing config (92 total,
\file{region\_tuple\_sweep\_n60\_v4.jsonl}) and, on its result, promotes atomic regions to the
production default for the tuple-ranking path: \code{router.py::get\_video\_priorities} now builds
the pool via \code{tuple\_ranking.atomic\_regions(bundle.artifacts.candidates)} instead of passing
\code{bundle.artifacts.regions}. Stage 3 clustering still runs and still feeds the independent-argmax
baseline and boundary-refinement seeding, both untouched and outside this ablation's scope.

\subsubsection{Round 7: clustering removed from the production retrieve path entirely}
\label{sec:tuple-round7}
Round 6 left Stage 3 clustering running for two remaining consumers: the independent-argmax baseline
and boundary-refinement seed selection. A further real check (not a benchmark re-run, a proof) found
clustering has \emph{zero} effect on either: \code{select\_event\_seeds}' exact returned timestamp
(refinement's sole input) was compared clustered-fed vs.\ atomic-fed for all 239 (event, video) pairs
in the $n=60$ corpus, and every top seed was byte-identical, gap $=0.0$, no exceptions --- not a
sample suggesting invariance, a proof of it, since both functions read only a region's member
candidates' own scores and timestamps, never merged-region span.

On that basis, clustering (\code{cluster\_temporal\_regions}) was removed from
\code{service.py::retrieve\_candidates} entirely and replaced with unmerged, one-region-per-candidate
construction (\code{atomic\_regions}, Section~\ref{sec:stage3}) for \emph{every} consumer, not just
tuple ranking. This first attempt broke two real tests: \code{replace\_frame\_scores} requires a
submitted frame score's timestamp to fall within its region's $[\text{start\_seconds},
\text{end\_seconds}]$ span, and a single-instant region ($\text{start}=\text{end}$) cannot satisfy
that for any timestamp but its own candidate's.

The fix separates two axes Round 6 had conflated: \emph{merging} candidates together and giving a
region \emph{width}. \code{atomic\_regions} gained an optional \code{margin\_seconds} pad (reusing
\code{ClusteringHyperparameters.margin\_seconds}'s existing default, 3.0s, rather than introducing a
new parameter) --- each candidate still gets its own unmerged region, now padded
$[\,t-\code{margin\_seconds},\,t+\code{margin\_seconds}\,]$. This is verified, not assumed, to be
free: the only place in \code{tuple\_ranking.py} that reads a region's span at all is a fallback for
zero-member regions, which a real atomic region never is, so padding cannot change ranking or
refinement output --- only which frame-score timestamps a region will accept. All 181 tests pass
(including both that failed on the first attempt), and a live end-to-end
\code{POST~.../artifacts/frame-scores} call against the restarted backend, with samples spread
$\pm2$s around a real padded region, succeeded (previously the exact failure mode). Stage 3 clustering
(\code{cluster\_temporal\_regions}, \code{merge\_overlapping\_regions}) is no longer called from any
production path --- kept in \file{algorithms.py} only as the comparison arm this and Round 6's
conclusions rest on.

\subsection{Production Integration}
\label{sec:tuple-integration}
The \code{threshold}@$0.5$, $w_o{=}0.8$, \code{pooling=max} configuration
was promoted from the benchmark tree
(\file{irrelevant\_things/benchmarks/youcook2/region\_tuple\_ranking.py}) into
\file{src/adaptive\_search/tuple\_ranking.py}, with the Section~\ref{sec:tuple-design}
correctness fix already applied, as an \textbf{opt-in} mode ---
\code{apply\_tuple\_ranking=true} on \code{GET .../video-priorities}, default
\code{false} pending validation beyond $n=60$. Round 4's two fixes
(Section~\ref{sec:tuple-round4}) extended this same production module rather
than replacing it: \code{build\_order\_constraints} is called from
\code{router.py} directly on \code{bundle.session.events}, so a live session
now supplies real, transitively-closed order constraints whenever the
rewrite stage classified \code{temporal\_relation} for it, with no benchmark
workaround required. As of Round 7 (Section~\ref{sec:tuple-round7}),
\code{bundle.artifacts.regions} itself is atomic (padded, unmerged) for
\emph{every} consumer, not just this path --- \code{atomic\_regions} lives in
\file{algorithms.py} now, next to \code{cluster\_temporal\_regions}, which it
replaced in \code{service.py::retrieve\_candidates}. This path's own call
site (\code{router.py}) accordingly simplified back to passing
\code{bundle.artifacts.regions} directly, with no special-casing --- the
special case Round 6 introduced (atomic regions for tuple ranking only,
clustered regions everywhere else) was a real intermediate state, not the
final one.

\begin{itemize}[nosep]
  \item \textbf{Ranking.} \code{TupleRankingHyperparameters}
    (\file{schemas.py}, defaults matching Table~\ref{tab:tuple-gate}'s winner)
    joins \code{SearchHyperparameters}. When requested, raw tuple scores ---
    unlike Eq.~\ref{eq:priority}, not bounded to $[0,1]$ --- are passed through
    \code{robust\_sigmoid} before overwriting \code{priority\_score}, the same
    normalization \code{assemble\_ordered\_tuples} already applies to its own
    raw scores (Section~\ref{sec:no-tuple}).
  \item \textbf{Refinement hand-off.} When \code{apply\_tuple\_ranking} and

    \code{\_video\_priority\_with\_boundary\_refinement}
    (Section~\ref{sec:stage5}) seeds each event from the winning tuple's own
    per-event timestamp instead of an independent
    \code{select\_event\_seeds} call --- the one piece of integration logic
    that delivers the \code{hits} improvement of
    Section~\ref{sec:tuple-results}, not merely the ranking improvement, and

    Section~\ref{sec:stage5}. Refined events are tagged
    \code{"source": "tuple\_ranking"} (vs.\ \code{"auto"} for independent

  \item \textbf{Verification.} 39 unit tests on synthetic regions

\subsection{Limitations}
\begin{itemize}[nosep]
  \item The 5 residually-regressed videos of Section~\ref{sec:tuple-round4} (all with
    independently low \code{hits\_baseline}) remain only partially mitigated under
    \code{threshold@0.5}. Section~\ref{sec:tuple-round5} tried the margin-based lever this
    limitation previously flagged as untried, at fine $\tau$ granularity, and it does not fix
    them either --- margin underperforms threshold at every tested cutoff, including on this
    same regression set. A fix for these 5 videos likely needs a different mechanism entirely
    (e.g.\ per-event rather than per-tuple confidence), not just a different signal under the
    same gate shape.
  \item Not benchmarked head-to-head against \code{assemble\_ordered\_tuples}
    (Section~\ref{sec:no-tuple}), which solves a related but distinct problem
    at a different pipeline stage (fine-grained ordering after dense
    per-frame scoring, not coarse video ranking); the two are complementary,
    not shown to be substitutable.
  \item All results are on one corpus (YouCook2 recipe videos, $n=60$ of 203
    available, whose events are near-uniformly causally sequential ---
    Section~\ref{sec:tuple-results}'s 100\%-\code{after} finding, confirmed
    across 176 classified pairs at $n=60$, is a property of this corpus, not
    a general claim about query structure). \code{during}/\code{simultaneous}
    handling in \code{build\_order\_constraints} is unit-tested on synthetic
    data only --- no video in this corpus exercises either branch on real
    data.
  \item Section~\ref{sec:tuple-round5}'s full atomic-region grid is still an aggregate-metric
    characterization: the matched per-video diff at the \code{default} point
    (Table~\ref{tab:tuple-clustering}) was not re-run at all 20 grid points, only at the one
    Round 4 already checked, since recall@$k$ aggregates are known to be able to mask a
    minority-regression pattern like that one.
\end{itemize}

  Accurate in shape; the previously-stated belief that ``coverage is purely
  informational, zero ranking weight'' needed correcting --- uncovered events
  are zero-filled into the mean, so coverage acts through the mean's
  denominator even though its explicit weight $w_c=0$. \\[4pt]

  \corr{Slightly overstated.} Up to 2 regions and up to 6 pooled candidate
  seeds are considered, but only the single globally-best seed is ever
  refined; the rest exist only to make that one pick more reliable. \\[4pt]

  Accurate for Stage 5's \emph{automatic} refinement
  (\code{radius\_frames}=10 default). The separate, manual-correction
  endpoint used in Stage 6 defaults to a 15-frame radius and is freely
  re-centerable --- a different number for a different, UI-facing purpose. \\[4pt]

  \corr{No literal tuple exists}; more precisely, up to $N$
  \emph{independently} refined per-event timestamps are attached to each
  video row, with zero joint optimization or consistency constraint between
  them --- which is the direct, demonstrated cause of the out-of-order/
